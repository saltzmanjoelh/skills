# builder

A Claude Code mod that watches the pull request a session names through its watch tool, as `/implement` does once it opens one. It wakes the session when the pull request changes, shows how far through `/implement` the work is above the prompt, shows the pull request and the session's agents in a pane, and owns the reviewer agents.

Install it from this repository's marketplace, which needs Claude Code 2.1.275
or later:

```
/plugin install builder --marketplace saltzmanjoelh/skills
```

To work on the mod itself, link this folder into the skills folder instead,
with the path to your clone of this repository in place of the placeholder.
The link loads the mod straight from your clone, so an edit takes effect
without reinstalling:

```bash
ln -s <path to this repository>/mods/builder ~/.claude/skills/builder
```

Use one way or the other, not both. When both are present, the installed copy
takes precedence and Claude Code skips the linked folder, so edits in your
clone stop taking effect until you uninstall the marketplace copy.

A session picks up the agents when it starts. A change to the hooks reloads in a running session.

## Upgrading from pilot

Builder used to be called pilot. Only the names changed: the tools are
`mcp__builder__*` instead of `mcp__pilot__*`, the agents are `builder:*`
instead of `pilot:*`, and the command is `/builder` instead of `/pilot`.
There is no alias for the old names, and a session that is already running
keeps them until it restarts.

If you loaded pilot through a link, the link points at a folder that no
longer exists once your clone has the rename. Replace it:

```bash
rm ~/.claude/skills/pilot
ln -s <path to this repository>/mods/builder ~/.claude/skills/builder
```

If you installed pilot from the marketplace, run `/plugin uninstall pilot`,
then `/plugin install builder --marketplace saltzmanjoelh/skills`.

Builder starts with an empty store. Claude Code keeps each mod's store in a
file named after the mod, and one mod cannot read another's, so builder does
not see what pilot kept. Any counsel decision still owed to a pull request is
dropped, and so is the record of what a session was already told, so a
session that watches a pull request again is told its state once more.

## What the session can call

| Tool or command | What it does |
|---|---|
| `mcp__builder__open_pane` | Opens the pane, as `/builder` does, and answers that it is open, or that it waits and is not drawn yet, quoting the engine's reason and adding that, when the reason is the terminal's width, typing `/builder` or widening the terminal shows it. A pane opened this way is drawn only from 144 terminal columns, and an app that places no panes never draws it. Takes no input. |
| `mcp__builder__progress` | Reports the stage `/implement` is in, with a `title` for the work and an optional `note` for a sub-step, and answers with the stage and the count, such as `builder: spec (2 of 9)`. The stages are `grounding`, `issue`, `spec`, `plan`, `build`, `verify`, `pr`, `review` and `merge`; any other is refused. The first report of a new title opens the pane once, unless it is already open. |
| `mcp__builder__watch` | Starts watching a pull request. Nothing is watched until this is called. |
| `mcp__builder__package` | Builds the review package for the head: `package.md` and `diff.patch`, kept in the git folder of the pull request's checkout, which is the worktree that has the pull request's head branch checked out. `package.md` holds `## Already decided`, the numbered items, `D1`, `D2` and so on, that the session's earlier verdict reviews and the branch's commit messages list under `Dropped:` or `Outside the spec:`, and `## Areas fixed so far`, read from the `Reviewed:`, `Area:`, `Tidied:`, `Retag:` and `Trend:` lines of the fix commits, with each area's streak of reviewed heads in a row that drew a fix there. Only an `Area:` fix, one that changed what the code does, counts toward a streak. A `Tidied:` fix, which changed only tests, comments, documentation, names or wording, is listed and counts toward none, and a `Retag:` line counts a mislabelled `Tidied:` line at its own commit. A `Reviewed:` value groups a commit under a head only when it has at least 7 hex characters and names exactly one commit on the branch; any other value is listed. When a streak reaches 3, the package says so at its top and in the first line of the tool's answer, whatever the findings behind the streak were, and the session puts the area to the counsel before any reviewer runs, saying that later safety findings and findings that break working behaviour in the area stay blocking whatever the answer. When git cannot read the commit messages, the tool refuses. |
| `mcp__builder__post_review` | Posts one comment review per round under the gh login. Its first line is `VERDICTS <sha8> spec=… adversarial=…`. |
| `mcp__builder__counsel` | Writes a counsel brief for a question the session would otherwise ask the person, and answers with the question's id and the brief's folder. Works with nothing watched. Its optional `pull_request` names the watched, open pull request that the decision is owed to; without it, the decision is recorded in the spec. Given `follow_ups` in place of `options`, a list of one to twenty follow-ups, it writes a follow-ups question instead, which never takes `pull_request` (see "The counsel"). |
| `mcp__builder__counsel_tally` | Counts the counsel's votes for one round of a question and answers with what to do next: go with the decision, ask the seven again, or ask the person. On a follow-ups question each member's entry gives `follow_ups`, its vote and reason for each follow-up keyed by the follow-up's number, and the answer gives every follow-up's decision, or says it was not decided and is dropped. |
| `/builder` | Opens the pane and answers as `mcp__builder__open_pane` does, except that when the pane waits it says only that widening the terminal shows it, since the person has just typed `/builder`. `/builder poll` reads the pull request now, `/builder watch <n>` watches one, and `/builder wakes` lists what woke the mod. |

A subagent may call none of these tools: agents report to the session, and the session alone writes to the pull request.

## What the band above the prompt shows

Builder counts as started from the session's first `mcp__builder__open_pane` call or `/builder` command, and from then on, for the rest of the session, the band above the prompt is always shown, except that it gives way to Claude Code's survey. It has two rows. The first is the progress bar, shown once a stage has been reported: the work's title, the stage and its note, the stages done out of nine, and the percentage, with a button under it naming how many agents the pane lists, running, planned and finished, which opens the pane or closes it when it is open. The count is the stages before the furthest one reported, so reporting an earlier stage changes the label but never lowers it. When the watched pull request has merged, the bar reads nine of nine and `merged`, whatever stage was reported last; when it closed without merging, the count stays and the label reads `closed`. Either way both rows stay until the session ends or a report with a different title starts new work, which resets the bar. A merge or close counts only for a pull request whose watch began after the title's first report. On the desktop, the mobile app and the editor the bar is one image, so the app cannot wrap its parts onto separate lines; in the terminal it is a row of text with the bar drawn in `█` and `░` cells, and when the row is too narrow it drops the title, then the stage, then the percentage, and then cuts with `…`. When the project names an issue address with the `Issue link:` fact and the title begins with an issue key, such as `ABC-123`, the key is a link that opens the issue: in the terminal it is the start of the row, until the row drops the title, which drops the link with it, and on the other surfaces it sits on its own row directly above the image, whose title then leaves the key out so the key is shown only once. The work at the top of the pane is drawn the same way.

The second row is the line. With a pull request watched, the line reads `builder: #<n> <state> · checks <result> · <what is next>`, and with something running it puts what runs before the last part: `builder: #<n> <state> · checks <result> · <what runs> · <what is next>`. With no pull request watched, as during the spec and the plan, it reads `builder: <stage> · <what runs>`, or `builder: <stage> · idle` when nothing runs, with `started` for the stage until one is reported. Before builder is started, the line shows with nothing watched only while something runs, as `builder: no pull request yet · <what runs>`, and the host's own line takes its place when nothing does. Pressing the line opens the pane, as `/builder` does.

When builder changed on disk since this session loaded it, the line begins with `builder changed on disk since this session loaded it; restart this session to load it`, followed by ` · ` and the rest of the line without its `builder: ` prefix. The rest is fitted to the width the warning leaves, and the warning itself is never cut: when the width is too narrow for more, or there is nothing else to say, the line is the warning alone, before builder is started too. The section "When builder changed on disk" says when this happens.

What runs is named in up to three parts. The session's own tool call is named once it has run for 10 seconds, as `running: <label> (<time>)`, where the label is a Bash call's description, else its command, else the tool's name; with several running, the one that started first is named. Questions to the person and Agent calls are never named this way, because the line already says it waits on the answer and names the agent. The running agents follow as `1 agent: <type>` or `<n> agents: <type>, <type>, …`, oldest first, with the `builder:` prefix dropped from their types. The agents come from the engine's own list, so an agent resumed with SendMessage, or one the mod did not see start, is counted too, and one the engine has finished or dropped is not. Last comes the background work, as `1 background command` or `<n> background commands` when every task is a shell command, and otherwise as tasks; a background subagent is counted once, as an agent. The list of that work is replaced by the one the engine reports at each end of the session's own turn and of each of its subagents; a subagent's end that reports no list leaves it as it was. A task also leaves the list as soon as the transcript draws its notification saying it completed, failed or was killed, so a command that finishes while the session is idle does not stay on the line until the next turn end. When the line is wider than the space above the prompt, agent names are dropped from the end first, and then the line is cut, ending with `…`. Descriptions, commands and summary lines are printed without control characters and cut to a fixed length, here and in the pane.

The last part says what the mod will do next and when it will next look at the pull request: a new head waiting to be handed over, an open question, running agents (left out when the agents are already named), running checks, a failed check waiting on a fix, a pending merge, or nothing to hand over, each followed by the time until that look (`in 7m` or `in under a minute`; once that time has passed it reads `handing over now` or `next look due now`). It says `not polling` when no look is scheduled, because nothing is watched or the pull request merged or closed. While a usage-limit hold is on, the last part reads `waiting on the usage limit until <time>` instead. With no pull request watched, that part comes after what runs, or takes the place of `idle` when nothing runs, and before builder is started the line shows it as `builder: no pull request yet · waiting on the usage limit until <time>` even when nothing runs. The section on the session going quiet says what a hold is.

The line stays current without a keystroke. The mod asks for a redraw every 30 seconds while a look is scheduled, so the time stays current, and every second while anything runs, so durations move by the second, reading the engine's list of agents again every fifth second, so finished work leaves the line. A read of the list that is slow is not started again while it runs. Once nothing runs, the list is read one more time before the mod stops asking for redraws, so an agent it did not see start, such as one resumed in the background, is still found. A call is named the moment it reaches 10 seconds, because the mod asks for a redraw then too.

The mod looks at the pull request about 10 seconds and again about 40 seconds after each of the session's own turns ends, which is how it learns of a commit the session just pushed; a short turn never cancels the later look of the turn before it. It also looks about 10 and about 40 seconds after a Bash call of the session's own that succeeded and ran `git push` (also with any number of `-c <key=value>` and `-C <dir>` options between `git` and `push`), `gh pr merge` or the project's merge command, even while the turn goes on, so the line does not say open for a pull request the session merged. A newer push or merge replaces the two looks still pending from the one before, and a push or merge that failed, or was moved to the background, is followed by no look. The command is only matched against fixed patterns; it is never passed to `gh`. Looks are numbered as they start. A look whose result arrives after a later look's result was stored never stores what it read and never changes the display. A look that records a state as already told still does so from its own read. A look that hands a change over hands over the newest read that a look of the same watch has stored and left for others to tell, under that read's number, and chooses it after its last wait before the prompt, so the session is told the newest state the mod shows. It hands nothing over when a newer read was stored by the look after posting a review or by the desktop app's CI event, or while either of those looks has stored a read and not yet told it, because that look tells the session its own read; a change found in that time is handed over by the next poll. A handover likewise does nothing when another read was recorded as told after it began reading what the session was last told, because what it read is then out of date; the next poll compares against the new record. Either does nothing once a newer read has been recorded as told, and a handover also does nothing when the read matches what the session was told. The labels the workflow sets itself, `in-review`, `waiting-on-author`, `ready-to-merge`, `stuck` and `needs-decision`, never wake the session: a change confined to them is not handed over, and the prompt for any other change leaves them out. The pane and the poll interval still read them. Between these looks the mod polls on a timer, as the next section says.

## How often it looks at the pull request

Every look runs one `gh pr view` of the watched pull request, and then one `gh api` read of the unfinished GitHub Actions workflow runs at the head that call gave. When that second read fails, the look goes on with the pull request's other facts, keeps the runs it last saw at the same head, and the state lines say the runs could not be read. Besides the looks after each of the session's own turns ends and after its own push or merge, described above, the mod looks at once when the desktop app's CI event arrives, which covers a failing check and a merge conflict. That event is the only one pushed to the mod. Between these looks the mod polls on a timer, and the first of the cases below that applies sets the interval. The names in parentheses are the keys of `POLL_MS` in `hooks/state.ts`.

- A new head that the session has not been told of: every 90 seconds. Nothing is pushed when the session's own push lands.
- An open question to the person (`owner`): every 10 minutes. The answer reaches the session without a look.
- A running subagent (`agents`): every 10 minutes. A background subagent's finish starts a turn of the session's own; a foreground subagent's finish returns inside the turn already running. Either way a turn of the session's own ends afterwards.
- Running checks or an unfinished workflow run (`ci`): every 90 seconds. A failing check is pushed by the CI event; a passing one is not, and neither is a run finishing, which may register no check at all.
- A failed check (`fix`): every 90 seconds. A rerun that fails the same way raises no event.
- The `ready-to-merge` label set (`merge`): every 90 seconds. Neither the checks finishing nor the merge landing is pushed.
- Nothing pending (`nothing`): every 10 minutes. Nothing anyone else does is pushed, a label change included.

The intervals are short where a change on GitHub's side is expected soon and only a look would see it, and long otherwise. The new head polls quickly until the mod has handed that change over. When the handover of that head was held, because the session's turn was running, or refused, its poll falls back to the interval of the next case that applies; a held change is still handed over when the turn ends, and a later head brings the 90 seconds back. A failed check counts as about to change because the session is fixing it or has rerun it. An open question keeps 10 minutes rather than more, because a look during the question is what notices a change made meanwhile and holds it for the end of the turn. A running subagent comes before the checks in the list, so running checks, a rerun of a failed check and a pending merge all wait 10 minutes while one runs. That is acceptable because the subagent's finish is followed by the end of a turn of the session's own, whose looks, described above, work the interval out again, so running checks are looked at 90 seconds later. A look that hands nothing over can bring the next poll forward but never puts off one already due sooner. While a usage-limit hold is on, the mod does not poll at all, whatever the list says, and it schedules the poll again when the hold clears, as the next section describes. The comment above `POLL_MS` points here, and whoever changes an interval updates this list, because no test reads it.

## When the session goes quiet, and when a usage limit runs out

The mod starts a turn of its own in two cases where a session left alone would otherwise wait until a person came back: when the session has been quiet for a long time with a pull request open, and when a usage limit stopped the session's turn. Both matter only to a session running `/implement`. The prompt for the first is called the stuck prompt below, and the state the second puts the mod in is called the hold.

The mod keeps the time the session last went quiet. That is the latest of four moments: the end of the session's own turn, the end of any of its subagents, a look that found the watched pull request changed, and the end of a usage-limit hold, so that a hold the person clears does not draw a stuck prompt at once. An agent whose end the mod learns only from the engine's list of agents counts too, from the read of the list that shows it ended. When the session has been quiet for the current interval, the mod starts a turn whose prompt says that nothing has happened on the pull request for that many minutes, tells the session to check with `gh` whether what it waits on is real, and tells it to take the first step of the list in `/implement` that applies, or to end the turn if the wait is real. The prompt names only the pull request's number and the minutes. It quotes no text from GitHub, so it adds nothing that someone else wrote to what the session reads.

The stuck prompt fires only when all of these hold at that moment: a pull request is watched and it is open; the session's own turn is not running; no subagent runs; no question the session asked with `AskUserQuestion` is unanswered; and no usage-limit hold is on. A `stuck` label on the pull request does not stop it, because only an open question counts as waiting on the person; a session that set `stuck` and ended its turn reads the label and the earlier answer and ends the turn again. The mod reads the engine's list of agents again just before it decides, so an agent the engine has dropped without the mod seeing it end cannot postpone the prompt for good. When the session's turn, a subagent or an open question is in the way, the prompt is postponed: the mod restarts the quiet time and looks again one interval later, or one interval after the end of a turn or of a subagent when that end restarts the quiet time first. When nothing is watched, the pull request is no longer open or a hold is on, the mod arms no stuck prompt at all; a new watch, a look that finds the pull request changed, or the end of the hold arms it again. The prompt is also dropped, and the quiet time restarted, when a change is being handed over at that moment, or a handover is waiting for the turn to end, or a look after posting a review or after the CI event has a read it has not told yet, because in each of those cases a turn about a real change is already coming. The checks on the session's turn and on the handovers are made with nothing in between that could wait, immediately before the mod submits the prompt.

The interval starts at 45 minutes and doubles after each stuck prompt the engine accepts: 45 minutes, then 90, then 180, then 360, and then 360 minutes every time after that, because six hours is the ceiling. The turn a stuck prompt starts does not reset the interval; when it ends, it only restarts the quiet time. The interval goes back to 45 minutes in three cases: when a look finds the watched pull request changed, when a new pull request is watched, and when the person starts a turn. A prompt counts as the person's when its origin is `composer`, `bridge` or `slack-ping`, or when its origin is `sdk` and it is not the desktop app's CI event, which the mod already tells apart by its text; a prompt typed in the desktop app arrives as `sdk`. A prompt the mod submits itself, whose origin is `plugin`, does not count, and neither does any other origin, such as `task-notification`. Answering a question is part of the session's turn, so it is not a reset; the session goes quiet again when that turn ends. Every other turn end, and every subagent's end, restarts the quiet time and leaves the interval alone, except a turn end that starts a hold, after which the end of the hold restarts the quiet time instead. A watch also restarts the quiet time, so after a new watch the stuck prompt counts from the watch.

The hold starts when the session's own turn ends with the reason `error`, the session is running `/implement`, and one of two signals says a usage window ran out. The first signal is the engine's usage report, `$.session.usage().rateLimits`, showing a window used at 100 percent or more. The second is the `StopFailure` hook reporting the error `rate_limit` for that turn. Either signal may arrive first, and the mod decides when it has both the turn's end and a signal. When the usage report cannot be read, the hold rests on the `StopFailure` signal alone. A turn that ends with an error and neither signal does not hold. The session counts as running `/implement` when a pull request is watched, or when the session has reported a stage with `mcp__builder__progress`, and in either case only while its work has not ended. The work has ended when the pull request the mod last read for it is merged or closed, which is the same test by which the progress bar shows the work as finished. A limit hit during the spec, the plan or the build therefore holds too, with nothing watched.

The hold resumes one minute after the latest reset time among the windows used at 100 percent or more. When there is no such window, or none of them gives a reset time, it resumes 15 minutes after the turn ended, and when the latest reset time is already past, it resumes one minute after the turn ended. The line shows the resume time in UTC, written as `/builder wakes` writes its times, with the UTC date before it when the resume is not on the same UTC day. A spend limit can read past 100 percent with a reset a month away, which is longer than the engine's longest timer of about 24.8 days, so the mod waits in steps of at most six hours and checks the time at each step; such a hold lasts until the reset unless the person clears it.

While the hold is on, the mod does not poll GitHub and no look runs, neither the looks after a turn ends or after a push, nor the look the CI event starts, with two exceptions: a `/builder poll` that the person asks for still reads the pull request, and so does the one read at the resume time. No stuck prompt fires during a hold. At the resume time the mod clears the hold and reads the watched pull request once, because a pull request merged or closed just before the limit may not have been read since; that read hands nothing over, and `/builder wakes` lists it as `resume`. With nothing watched, as in a hold during the spec or the build, there is nothing to read. Then, only if the work has not ended, the mod starts a turn telling the session that the usage limit has reset and that it should carry on `/implement` from the stage it was in, naming that stage when one was reported, and then polls as it did before the hold. If that turn dies on the limit too, the hold starts again by the same rule, with a fresh resume time that replaces the old one. When a turn is already running at the resume time, the mod clears the hold without a prompt, because the end of that turn decides again by the same rule. A hold that finds the work has ended by its resume time, by that read or by an earlier one, clears itself without starting a turn. A turn of the session's own that ends with an answer or a refusal during the hold also clears it, with no resume turn, whatever started that turn, because the API replied to it; a turn the person interrupted leaves the hold as it is. The person starting a turn during the hold clears it at once, with no resume turn, and the mod polls again from then on; a prompt of the person's that arrives as the resume time falls is the only one that goes out. A prompt of the person's that arrives after a turn the limit stopped has ended, while the mod is still deciding whether to hold, starts no hold, because that prompt would have cleared it.

When the engine refuses a stuck prompt, the mod restarts the quiet time and tries again one interval later, without doubling the interval, because the refused prompt never reached the session. When the engine refuses the resume prompt, or the submit fails, the mod holds again and tries 15 minutes later. When the mod cannot clear the hold at the resume time, it sends nothing and tries again 15 minutes later, so the hold does not last until the person types. Once the hold is cleared, a failure to save the restarted quiet time does not stop the resume: the mod still decides whether to send the resume prompt, and it arms the stuck prompt from the moment of the clear all the same. When the mod cannot read its own state at the moment a stuck prompt or a resume falls, it sends nothing then and tries again: the stuck prompt one interval later, counted from that moment, and the resume 15 minutes later. A failed read therefore postpones either prompt but never ends it.

The quiet time, the interval and the hold live in the mod's in-memory state, which survives a hot reload of its hooks but not a restart. The timers themselves do not survive a reload, so the mod arms them again from that state when its hooks next run, and a hold or a stuck prompt still comes at its original time. A restarted session starts with no hold and with the interval at 45 minutes, and its stuck prompt counts from its watch.

## When builder changed on disk

The mod is usually loaded through a link into a git checkout, so the checkout can move on while a session runs, and the session then runs a version of builder different from the one a restart would load. The mod finds that checkout by resolving its own folder, with links followed, and runs git there. It records two commits of that checkout:

- **The session commit** is the checkout's `HEAD` at the session's first start, and it is never rewritten in that session. It stands for the files the engine reads only when a session starts: `agents/`, `.claude-plugin/plugin.json`, and `hooks/hooks.json`, the list of hook modules.
- **The hooks commit** is the checkout's `HEAD` at the newest load of the hooks module: at the session's start and at every hot reload. It stands for the rest of `hooks/`.

Both commits are kept in the `loaded` state in memory, which survives a hot reload of the hooks but not a restart, and a restart records them again. That is why the session commit is never rewritten within a session.

The mod compares them with the checkout's `HEAD` when its hooks load, at the end of every turn of the session's own, and on each poll of a watched pull request, so a session with nothing watched finds out by its next turn end. A comparison reads `HEAD` first and does nothing more when `HEAD` is the one the last comparison read. Otherwise it runs `git diff --quiet <commit> <commit read> -- <paths>` for each recorded commit that is not the commit it read, naming that commit rather than the word `HEAD` so the diff compares exactly what was read, and keeps what it found only if `HEAD` has not moved again meanwhile. The line and the pane warn when the session's files differ between the session commit and `HEAD`, or the other hooks files differ between the hooks commit and `HEAD`. Which way the checkout moved does not matter: a fast-forward, another branch checked out and a reset to an older commit all warn when those files differ, and a move that touches none of them, such as one touching only files outside the mod's folder or only its README or its tests, says nothing. A folder that is not a checkout, and a git command that fails, say nothing either.

The warning clears at the next comparison once `HEAD` comes back to files equal to the ones loaded. A hot reload clears a warning that was only about `hooks/` files other than `hooks/hooks.json`, because the reload records a new hooks commit and so loads those files. A warning about the session's files clears only with a restart. A session that started under an older builder, one that kept no record of these commits, warns as soon as a hot reload loads this one, because the commit it started at is unknown, and that warning also clears only with a restart. The cure is a restart rather than a reload because the engine offers no call that reloads a plugin, and the agents, the manifest and the list of hook modules are read only when a session starts. The comparison is between commits, so edits in the checkout that nobody committed are not seen.

## The pane

When builder changed on disk since this session loaded it, the pane begins with the same warning as the line, in yellow, whether a pull request is watched or not. After it, the pane begins with the work: the title, the stage and the same bar as the band. Then it shows the watched pull request, its labels, checks, verdicts and round, then every agent of the session, then the background work, any open question, the counsel and the next step. Each agent has one row with its type (without the `builder:` prefix), its description, the model the engine spawned it on (a hyphen, `-`, for one the mod did not see spawn), its status, how long it has run or ran, and its summary line once it finished: its end line (`LENS-END`, `CLAIMS-END` or `VERDICT:`) when it has one, else the start of its answer. There is no progress bar per agent. Running agents come first, then the planned ones, then the finished ones, folded under one `Finished · <n>` button that unfolds and folds them; the running and the finished come newest first, and a finished row stays for the life of the session, even after the engine drops the agent from its list. An agent the engine drops while the mod still has it as running shows `no longer listed` in place of its status, with the finished agents and with its time frozen at when the list last named it. Each background task has a row with its status, type and description or command. Before a pull request is watched, the pane says so and still lists the agents and the background work above the counsel, so pressing the line always shows what it named. On the desktop, the mobile app and the editor the work and each agent row are one image each, with their buttons on their own rows below; the pull request, the counsel and the next step are text everywhere.

The planned agents are worked out by the mod, never reported by the session. After a package call at the watched head, while the pull request is open, the four focused reviewers that have not started since are planned; once all four have finished since, the spec and adversarial reviewers that have not started since are planned. While a counsel question has no tally for its current round, the members its last answer told the session to launch, and that have not started since, are planned. A type is listed once, and nothing planned is stored, so a planned row goes as soon as its cause does.

Each agent row has an `output` button that opens a second pane, `builder agent`, with the agent's type, description, model, status and time, what it was asked, and its last 40 messages as the engine holds them: its text, and each tool use as the tool's name and a short summary of its input, all printed without control characters. The pane opens as soon as the button is pressed and says `Reading the messages.` until the read answers. While the agent runs, the messages are read again on each read of the engine's list, and once more when it ends. When the engine refuses the read, or it fails, the pane says so and why, and still shows the agent's card.

When the session starts, and when the mod's hooks load again after a hot reload, every question still marked unanswered is marked answered and the `needs-decision` label the mod put on for it is taken off, because the mod can no longer see whether that call is open. The records of the session's own calls in flight are cleared at the same moment, for the same reason. A question the session asks while `needs-decision` is already on the pull request counts as one the mod labelled, so the mod takes the label off once no question is open. That matters after a restart: the restarted mod has no record of a question the killed session left open, so its label stays on, and when the resumed session asks again, the new question takes the label over and the label comes off once it is answered. The mod cannot tell who put the label on, so a label that a person or another tool put on also comes off once the session's question is answered; this is accepted because the mod manages the label itself.

## The agents

`builder:spec-reviewer` and `builder:adversarial-reviewer` give the verdicts. `builder:security-reviewer`, `builder:maintainability-reviewer`, `builder:performance-reviewer` and `builder:data-reviewer` each look at one kind of problem. Those six may only read and hand their report back; the mod refuses them every other tool. Every finding they report carries a `Scope:` line, saying whether the spec asks for the behaviour, whether the head breaks behaviour that works on the base branch, or whether it is outside the spec, and a finding outside the spec is not fixed in the pull request. They read the package's `## Already decided` section first, and raise a decided item again only with evidence it did not have, on a `Repeats:` line. When a prompt names a counsel brief instead of a review package, each of the six votes on the question from its own angle instead of reviewing, ending with a `VOTE:` line (an option's number or `none`) and a `REASON:` line. `builder:owners-advocate` sits on the counsel only and is never launched in a review round. It judges each option by what the owner has already written, which is the global and project `CLAUDE.md`, the issue and its stated reason, the spec and the decisions already recorded, and votes `none` only when none of those settle the question, naming in its `REASON:` line the preference that is missing. The mod holds it to the same read-only tools as the reviewers. `builder:claim-checker` tries to refute findings and may run commands it builds itself. It also checks every finding's scope against the spec and the base branch, and a scope it cannot settle counts as outside the spec. `builder:bug-reproducer` finds the smallest reproduction of a reported bug.

## The counsel

Before a session asks the person a question, it puts it to the counsel: the six read-only reviewers and the owner's advocate, seven members, each launched with "Counsel brief: <folder>.". The brief, `brief.md`, holds the question, two to four options in the order given, the background and the paths the question touches. It never holds the session's own lean, and members never see each other's votes. Every member votes on every question, judging it as an engineer and bringing its own angle where the angle applies. It votes for one option, or votes none when no option is right or when only the person can answer, because the answer depends on what they want or on a fact about their business; a member may propose a new option only when it votes none.

The mod counts the votes only when every member has one. A member that abstained, failed, was stopped or gave a vote that cannot be read has no vote: the tally refuses the round, names those members, and records that they were asked again, and the session launches exactly them again and tallies the round again with every vote. A member asked again that still has no vote in the same round sends the question to the person, and the answer names the members that were asked twice. When the mod's record of agents holds no agent of such a member's type started since the members were last launched, and the member gave neither a reason for abstaining nor a vote that cannot be read, the answer says that the member never started in this session, and tells the session to add that restarting the session lets the counsel decide again only when the Agent tool answered that the member's type was not found, as it does in a session that started before the member joined the counsel. Each round asks again on its own. A counted round has seven votes, and when a strict majority of them, which is 4, chose the same option, the counsel decides, and the session goes with it and tells the person in the words the tally gives, such as "The counsel chose: X. 4 of 7 members voted for it.", with the option exactly as the session wrote it, ending in one full stop, question mark, exclamation mark or ellipsis. The owner chose the strict majority; two thirds of seven would have needed 5. When the first round does not decide and a member that voted none proposed a new option, the mod adds it to the brief and the seven vote once more; there is never a third round. Otherwise the question reaches the person with the options ordered by votes, why the counsel did not decide, one line of reason per member that voted, any members without a vote with their reasons as a separate list, and the session's lean. The person can overturn a decision by telling the session. The pane lists the counsel's questions, newest first, with the tally, and, under "Without a vote:", the label the question put to the person uses, any members without a vote, which appear only in a round sent to the person, in tallies recorded before every member had to vote, and as the owner's advocate in tallies recorded before it joined the counsel, and the mod adds each decision that is owed to a pull request to the next review the session posts on that pull request.

A vote the mod can read is an option's number, written alone or as `option N`, or `none`. The vote may be wrapped in Markdown emphasis, such as `**2**`, and a number may be followed by one remark in brackets, such as `2 (a 5-minute poll)`, as long as the remark does not start with the word "or" or "and". So `2 (or 3)` cannot be read, and neither can `2 or 3` or `two`. When a vote cannot be read, the tally's refusal that asks for the member again, and the answer that asks the person, quote the first line of what the member wrote, cut to at most 80 characters, so that the session and the person can see it. When that text looks like a secret, the answer says it was withheld instead of quoting it. The pane still says "no readable vote" for that member, and the text is stored nowhere.

A decision is owed to a pull request only when the session named it with `pull_request` in the counsel call, and only when that pull request was the watched one and open at that moment. Any other decision is recorded in the spec instead, as the tally's answer says. When a round decides such a question, the tally asks GitHub for that pull request's state, whatever the watch follows by then, and the decision is owed to it only when GitHub says it is open. When it merged or closed, or its state could not be read, nothing is owed, and the answer says why and tells the session to record the decision in the spec. A decision owed to a pull request that merges or closes before the next review is listed in the turn the mod starts for the merge or the close, and in the watch tool's answer on that pull request, which reaches a session resumed after a restart; either one tells the session to record it in the spec and deletes the keys it listed. When `pull_request` is not the number of the watched, open pull request, because another pull request is watched, the watched one has merged or closed, or nothing is watched, the tool refuses the call and writes no brief. Its answer says what is watched and its last known state, so that the session can call again with that number or with none.

A follow-ups question is how an `/implement` session asks the counsel what to do with the follow-ups of a review round that it did not fix itself. The session calls `mcp__builder__counsel` with `follow_ups` instead of `options`, each follow-up in one or two sentences, and the mod gives every follow-up the same three options: fix it in this pull request, file it as an issue, or drop it. A follow-up passed as `{ text, outside_spec: true }`, for a finding outside the spec, is offered only file and drop, keeping their numbers 2 and 3, and a vote to fix it is not counted: the tally asks that member again and says the follow-up cannot be fixed in this pull request. The brief numbers the follow-ups, and each member ends its report with one `VOTE n:` line, holding `fix`, `file`, `drop` or `none`, and one `REASON n:` line per follow-up, and proposes no new option. Each follow-up is decided on its own when at least 4 of the 7 chose the same option, and is otherwise dropped as undecided. A member still without a vote for some follow-up after being asked again does not send the question to the person, as it would for any other question: each follow-up is counted from the votes that exist, so one with 4 votes for an option is still decided, and the others are dropped with their tally and the members without a vote. The owner chose this for follow-ups questions only. A follow-ups question never reruns, refuses `pull_request`, and is owed to no review and recorded in no spec, because the session writes each decision into its review's **Follow-ups** section. A call with both `options` and `follow_ups`, with an empty list or with more than twenty follow-ups is refused and writes no brief. The pane lists a follow-ups question with each follow-up's tally and decision.

Three questions never go to the counsel, because they are about the pull request's own safeguards and the counsel is made of the agents that review it: whether to merge a head with no checks when checks were expected, what to do when a limit on pushes or rounds is hit, and a check that failed for a reason outside the code.

## What it reads from the project's CLAUDE.md

Each fact is one `Label: value` line anywhere in the file.

| Label | Default | Used for |
|---|---|---|
| `Architecture document:` | `docs/architecture.md` | Named in the package for the data and security reviewers, if the file exists |
| `Gotchas document:` | `docs/gotchas.md` | Named in the package, if the file exists |
| `Merge command:` | none | Its words before the first `<` mark a Bash command of the session's own as a merge, after which the mod looks at the pull request soon; it is read once when the session starts |
| `Issue link:` | none, so issue keys stay plain | The issue address, such as `https://tracker.example.com/issue/{key}`, with every `{key}` replaced by the key at the start of the bar's title, which turns that key into a link in the band and the pane. It must begin with `https://`, contain `{key}` and hold no spaces or control characters. When the project's `CLAUDE.md` lacks the line, it is read from the `CLAUDE.local.md` beside it, and then from the `CLAUDE.local.md` in the repository's main checkout when the session works in a git worktree of it; the first file with the line wins. It is read once when the session starts, and again after a hot reload. A fact that cannot be used leaves the keys plain and shows one toast naming the reason, such as `builder: the Issue link fact was ignored because it has no {key}` |

## The status file for the foreman

The foreman is a mod for a parent session that runs several `/implement` sessions. It reads one JSON file per session it started, on its own timer, to see which of them need a person, which are idle and which are done, without spending the parent's tokens. Builder writes that file, and only in a session whose first prompt holds a line `foreman-ticket: <value>`. The value is the rest of the line with the white space around it removed, and a line with nothing after the colon counts as no ticket. The foreman adds the line to the prompt it starts a session with, so a session the owner starts by hand never writes a file.

The first prompt is the first user message of the session's transcript that has text, read at the first prompt builder sees, so a resumed session finds the ticket of its original first prompt. When the transcript holds no such message yet, or cannot be read, the prompt being submitted is checked instead. A transcript longer than the 4096 entries the engine returns starts after the first prompt, and then no ticket is found. The answer is kept in the mod's state, so a hot reload does not look again. A `/clear` ends the session under its old id and drops the ticket with it, and the new conversation looks for a ticket in its own first prompt.

The file is `<config>/foreman/builds/<session id>.json`, where `<config>` is the `CLAUDE_CONFIG_DIR` variable when it is set and `$HOME/.claude` otherwise. Nothing is written when that folder is not an absolute path, or when the session id holds anything but letters, digits, underscores and hyphens, so the file cannot land outside the builds folder. Builder works the record out again whenever its own state changes and at each event that can change the record (a permission prompt, a failed tool call, the cleanup skill), and writes the file when the record differs from the one last written in any field but the write time. It also writes the file at least once a minute while the session lives, with a new write time even when nothing else changed, so a file whose write time stops moving tells the foreman that the session is gone or hung. Writes go one at a time, and a change that arrives while a write runs is written after it, so the newest record is normally the last one written. The one exception is a write that runs past 30 seconds: builder gives up waiting for it, and it can still land over a newer record until the next change or the next minute's write replaces it. Every write replaces the whole file. The engine offers no way to rename a file into place, so a reader that catches a file in the middle of a write sees text that does not parse, and reads it again. A write that fails is dropped, and the next change or the next minute's write tries again.

When the session ends after its pull request merged, builder deletes the file with `rm -f`, because the engine's file interface has no delete. That runs inside the engine's short budget for ending a session; when it fails or is cut off, the file stays and reads `done`, or `in-cleanup` when the cleanup skill had started, either of which tells the foreman the session finished its pull request. When the session ends without a merge, the file stays for the foreman to read. Nothing is written after the session's end.

| Field | What it holds |
|---|---|
| `version` | `1`, raised whenever a field changes meaning |
| `sessionId` | the engine's session id, the same as the file's name |
| `ticket` | the value of the `foreman-ticket:` line |
| `desktopSessionId` | the desktop app's session id, from the `CLAUDE_CODE_HOST_SESSION_ID` variable; left out when that variable is unset |
| `cwd` | the folder the session started in, so the foreman can find the session before it knows the desktop id |
| `issueKey` | a leading issue key, such as `ABC-123`, of the title last reported through the progress tool, or null when there is none |
| `issueTitle` | the rest of that title, or the empty string before any report |
| `stage` | the stage last reported through the progress tool, or null before any report |
| `stageDone` | the stages done out of nine, as the bar above the prompt counts them: 0 before any report, and all nine once the watched pull request merged |
| `pr` | `{ repo, number, state, checks }` of the watched pull request, where `state` is `OPEN`, `MERGED` or `CLOSED` and `checks` is `none`, `pending`, `passed` or `failed`; null before a watch has read it |
| `state` | one of the six states below |
| `reason` | one line that says why the state holds |
| `stateSince` | when the state began: the time of the write at which it last changed, kept across a hot reload |
| `writtenAt` | when the file was written |
| `cleanup` | `{ failedCalls, lastError }` once the cleanup skill has started, whatever the state; left out before |

Every time is milliseconds since the epoch. The types are `BuildStatus`, `BuildState` and `BuildStage` in `types/index.d.ts`, so the foreman can name builder as a dependency and type-check its reader against them.

The state is the first of these that holds, in this order:

1. `needs-you`: an `AskUserQuestion` call of the session's own is open; or a counsel tally answered that the person must be asked, and since then neither has an `AskUserQuestion` call that started after the tally ended come to an end nor has the person sent a prompt; or a permission prompt is open. A permission prompt counts as open from the classic `PermissionRequest` event until the same loop's call of the same tool returns, or that loop's turn ends, where the loop is the session's own or one subagent's. A new turn of the session's own also closes the session's prompts, and a subagent's prompt no longer counts once its agent has stopped running.
2. `working`: the session's own turn runs, or an agent, a background task or a tool call of the session's own runs.
3. `waiting-on-builder`: builder has a look at the pull request scheduled, or a usage-limit hold is on.
4. `in-cleanup`: the `cleanup` skill, or a plugin's skill whose name ends in `:cleanup`, has started in this session. It lasts until the session ends, even when the cleanup refuses.
5. `done`: the watched pull request merged.
6. `idle`: none of the above.

So `done` and `in-cleanup` show only once nothing runs, and the foreman sees `done` only when the merged session has stopped working.

The cleanup record counts every failed tool call since the cleanup skill started, the session's own and its subagents', and keeps the last line of the newest error that is not blank, cleaned of control characters and cut to 200 characters. A line that looks like it holds a secret is replaced by `(withheld: it looks like a secret)`. The record never copies a tool's input, which can hold commands, paths or secrets, and a permission prompt's reason names the tool only.

The permission prompts, the failed calls and the cleanup skill reach the mod through classic events and `skill.prompt`, which the engine does not raise for a plugin a person installs where an organization manages Claude Code. There the file still shows every other state, but never a permission prompt or the cleanup.

## What it keeps

GitHub is the record. The package and review tools write `package.md`, `diff.patch` and `review.md` under the git folder of the pull request's checkout, in `builder/<sha8>/`, where they are never committed and go away when the worktree is removed. Each time the package tool or the review tool runs, it finds that checkout with `git worktree list`, as the worktree, the main checkout included, that has the pull request's head branch checked out. When no worktree has that branch, or git cannot list the worktrees, it uses the session's folder instead, and the package tool runs its git commands there too. The counsel tool still uses the folder the session started in. `$.store` keeps, per session and pull request, the snapshot last handed to the session, so a restart does not hand the same state over twice, and the time the session last looked at that pull request, refreshed once a day. It also keeps each decision the counsel made on a question that named the watched, open pull request, until a review posted on that pull request lists it, under a key of its own, `counsel-owed:<repo>#<number>:<session id>:<question id>`. Each decision has its own key because the store has no atomic update, so sessions sharing one list per pull request could erase each other's decisions. The review tool lists every key under its pull request, so a restarted session, or another session posting on that pull request, still lists them, and it deletes the keys it listed once gh confirms the review is posted. The turn the mod starts for a pull request that merged or closed, once the prompt is accepted, and the watch tool's answer on such a pull request also list its keys and delete the ones they listed, so a decision owed after the list was read is listed the next time. When a session starts, it prunes the records of pull requests that no session has looked at for two weeks, and each owed decision made more than ninety days ago. An owed decision is kept that much longer because a pull request that ended while no session watched it is learned of only when a session watches it again.

In a session the foreman started, the status file under the configuration folder holds what the session is doing, and it is deleted when the session ends after a merge (see "The status file for the foreman" above).

The counsel tool writes each brief to `<git dir>/builder/counsel/<session id>/<id>/brief.md`, beside the review packages and likewise never committed. The session id is in the path because every session in a checkout shares its git folder. The questions themselves are kept in the `counsel` state in memory for the pane, like the session's other state, so a restart loses them, together with the record of which members were asked again, and a vote in progress must be asked again. A decision already owed to a pull request is not lost, because the store keeps it until a review lists it. A restart begins the ids again at c1, so the tool never writes over a brief that is already there: it skips each id whose folder already holds a brief and takes the next free one, leaving the earlier briefs alone. Only if the next 100 folders all hold briefs does it answer that the counsel could not sit. The state keeps only the newest 20 questions.
